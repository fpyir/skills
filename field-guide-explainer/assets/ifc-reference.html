01 /

A graph, written as records.

The header gives you context. The data section gives you entities. The schema gives their positional attributes meaning.

example.ifcIllustrative exchange
ISO-10303-21; HEADER; FILE_DESCRIPTION(('Parser example'),'2;1'); FILE_NAME('example.ifc','2026-09-21T00:00:00', ('Author'),('Org'),'Writer','App',''); FILE_SCHEMA(('IFC4X3_ADD2')); ENDSEC; DATA; #30=IFCPOLYLINE((#10,#20)); #10=IFCCARTESIANPOINT((0.,0.,0.)); #20=IFCCARTESIANPOINT((10.,0.,0.)); ENDSEC; END-ISO-10303-21;

Context before content.

FILE_SCHEMA selects the IFC schema. FILE_DESCRIPTION declares the exchange implementation level; FILE_NAME carries provenance. These are different concerns: “IFC4X3_ADD2” identifies the data model, while “2;1” identifies the exchange profile.

This is a serialization example, not a complete building model. Conventional IFC uses this compact envelope. Full Part 21 has additional, edition-dependent constructs; define your supported profile.

Preserve the distinctions

Unset, derived, empty aggregate, and empty string are different values.

Common simple-record path · simplified

record    := ref '=' name '(' args? ')' ';'
args      := value (',' value)*
value     := scalar | ref | '$' | '*'
           | '(' args? ')'
           | name '(' value ')'

Predict. Don’t backtrack.

A byte dispatch and a small nesting stack are enough for this path. Each frame tracks whether it expects a value, a comma, or a close. Counting parentheses alone cannot catch missing separators.

This sketch is not a full Part 21 grammar. Complex instances and newer exchange features need additional productions.

04 /

Build around memory movement.

The fast path reads bytes, recognizes structure, and writes compact output. Avoid making an object for every token.

01 · Scan

Find structure.

Track strings, comments, and delimiters. SIMD can classify many candidate bytes at once; lexical state decides which matter.

02 · Parse

Consume directly.

Use predictable byte dispatch and an explicit nesting stack. Convert values only as required by the output contract.

03 · Store

Write compactly.

Use contiguous value buffers, type IDs, and aggregate ranges. For extraction, write directly into required columns.

04 · Link

Resolve IDs.

Build the reference index. Check duplicates and unresolved targets. Schema validation and geometry follow separately.

Think buffers, not object forests.

A directory maps each entity ID to its type and value range. Lists point into a shared buffer. These are logical stages—you can fuse them without intermediate token arrays.

Entity #30 → type: POLYLINE · values: [0, 1)

0 · LIST(1,2)1 · REF(10)2 · REF(20)3 · …

Keep source offsets for diagnostics. Decode retained string spans on demand.

Zero-copy has a lifetime.

Borrowed strings require the source buffer to stay alive. A streaming reader that releases chunks must copy retained values or keep backing storage. Validate encoding even if decoding is deferred when promising full validation.

IDs need a density-aware index.

Use a direct array for dense IDs; a paged structure or hash table for sparse ones. Never size an allocation solely from the largest untrusted ID. Guard numeric overflow and nesting depth.

Parallelize after measuring.

Split at confirmed record boundaries, never arbitrary semicolons. Private worker arenas avoid allocation contention. A boundary pass adds traffic and serial work; a giant record can still dominate one worker.

Borrow the technique, not the benchmark.

SIMD structural scanning has proven effective for JSON. STEP requires different quote, comment, and encoding logic. JSON throughput is not an IFC speed guarantee.

Architecture recommendations are engineering judgments. Related research: Parsing Gigabytes of JSON per Second.

05 /

Where is the speed limit?

Linear work is optimal for full parsing. The GB/s ceiling depends on your machine, your input, and what you promise to produce.

Θ(N)

Full validation must inspect the input.
A deterministic parser can do linear work under bounded-cost scalar processing.

Once the algorithm is linear, the real question is how much CPU work and memory traffic each input byte creates. A faster scanner cannot erase the cost of an oversized output.

The smallest ceiling wins. Decimal GB/s. Bars rescale together. Real throughput is lower when stages fail to overlap, or incur serial work, contention, cache misses, and scheduling overhead.

R ≤ min(Binput, Bmemory / a, p × f / c)

a = memory traffic per input byte · p = effective cores · f = clock frequency · c = cycles per input byte

ContractWhat it producesWork beyond scanning

Geometry evaluationShapes or meshesA separate algorithmic workload, not “parsing speed”.

Numbers can become the bottleneck. Coordinate-heavy files spend real time converting decimal text to binary floating point. Use a correctly rounded converter with fallbacks; a naive multiply-and-add loop is not equivalent. Number parsing research.

The implementation brief

Start compact.
Measure the whole path.

One pass is a useful starting point. The best final design depends on the output you actually need.

  1. Fuse a byte scanner with a predictive parser.
  2. Write compact buffers; avoid per-token allocations.
  3. Resolve references without recursively loading targets.
  4. Measure scanning, conversion, storage, and linking separately.
  5. Add SIMD and parallel batches where measurements justify them.
